Backup and Recovery

This page describes how Acme Cloud backs up production PostgreSQL data and the process for restoring it.

Backup schedule

Full PostgreSQL backups run daily. In addition, write-ahead log (WAL) shipping enables point-in-time recovery (PITR) for any moment within the retention window.

  • Full backup frequency: daily, during the low-traffic window.
  • PITR retention: 7 days.
  • Backups are stored encrypted, in a separate cloud region from the primary database.
  • Backup integrity is verified weekly by an automated restore into an isolated staging environment.

Restore procedure

Restoring production data is a high-risk operation and follows a strict approval process.

  1. Identify the target restore point (either "latest full backup" or a specific PITR timestamp).
  2. If the restore is happening during an active incident, the restore must be approved by the incident commander before proceeding. Outside of an active incident, restores require sign-off from a platform-data team lead.
  3. Provision an isolated restore target — production restores are never performed directly in place without first validating the restored data.
  4. Run the restore using the internal pg-restore-tool, specifying the backup identifier or PITR timestamp.
  5. Validate row counts and spot-check critical tables before cutting traffic over.
pg-restore-tool \
  --target isolated-restore-01 \
  --pitr-timestamp "2026-03-10T09:15:00Z" \
  --approved-by ic:jrivera

What backups do not cover

Object storage (uploaded customer files) is replicated independently and is not part of the PostgreSQL backup process described here. Application configuration and secrets are versioned separately in the infrastructure repository.
